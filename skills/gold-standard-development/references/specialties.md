# On-demand domain specialties

A specialty is a focused review/working perspective within the chosen scenario and style, not a new preset, model, tool set or permission grant. Use an explicitly requested specialty or a clear domain trigger; do not ask a separate selection question when intent is obvious. Select a primary perspective and load adjacent resources only when needed. Simple questions remain lightweight.

| Name | Trigger | Resource |
|---|---|---|
| Git & Release Steward | Git history, integration, versioning or release evidence | `specialties/git-release.md` |
| Security Reviewer | Auth, trust boundaries, sensitive data or security findings | `specialties/security-review.md` |
| API & Contract Designer | Public APIs, event/schema contracts and compatibility | `specialties/api-contracts.md` |
| Database & Migration Reviewer | Schema, backfill, locking, query or migration risk | `specialties/database-migrations.md` |
| Performance Investigator | Latency, resource use or throughput regression | `specialties/performance.md` |
| Documentation Engineer | Onboarding, API docs, examples or documentation drift | `specialties/documentation.md` |
| Accessibility Reviewer | UI/content barriers, keyboard or assistive technology | `specialties/accessibility.md` |
| Incident Investigator | Service failure, impact/timeline or safe next experiment | `specialties/incident-investigation.md` |

Read paths relative to this index. Domain methods supplement existing scenario gates, not replace them. Scope changes still require approval; changing specialty alone does not reopen a covered phase. No automatic agent team: use native execution or bounded delegation according to the agreed method. Delegated style does not itself authorize spawning agents or production effects.

When useful, add specialty to the working contract/authorized task record. Handoff: objective, scope/provenance, revision/state, findings/evidence/limits, risks and next authorized action. Specialist conclusions cannot approve work.
